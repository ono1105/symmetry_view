## 1. 方針転換の経緯

### これまでの旧方針 (csp_v2)
- pygame + PyOpenGL で「結晶対称性パズル」を直接作る
- 32点群分のシナリオ(原子配置)を手書きで設計
- 各シナリオの真の最大群を `validate_scenario.py` で検証
- 中学生モード/大学生モード、ミスカウント、罠、クリア演出など、ゲーム機能を中心に組む

### 旧方針で直面していた問題
- 「単一 species で C3 を作ると σv が自動的に出て C3v になる」など、低次点群を手作りで実現する難しさ
- 六方軸でのフラクショナル座標表現の複雑さ
- 32点群分のシナリオ手書きの作業量
- accidental symmetry の混入リスク
- 「ゲーム」としての設計と「結晶学の教育」としての設計の食い違い

### 新方針 (今回確定)
**「ビューアーを先に作り、後からパズルを載せる」**

- pymatgen + spglib + PyVista + PyVistaQt に技術スタック変更
- 任意の CIF を読み込んで対称性を可視化するビューアーを作る
- spglib が空間群対称操作を直接返すので、原子配置を手で設計する必要がない
- パズル機能はビューアー完成後に上に乗せる

### この転換のメリット
- 旧方針で詰まっていた問題が全部消える(spglib が対応するため)
- 実在の結晶構造(NaCl, ダイヤモンド, ペロブスカイト等)と直接結びつく
- ビューアー単体でも価値のあるツールとして成立する
- 段階的に開発できる(段階1 → 段階2 → 段階3)

## 2. 確定した方針(全項目)

### プロジェクトの位置づけ
**結晶構造ビューアー + 対称要素ビューアー を先に作り、その上にパズル要素を組み込んでいく**

- ビューアーが基盤、パズルは応用
- ビューアー自体が単体で価値のあるツール(VESTA 風)
- パズル化の段階でゲームシステムと UI を再設計する

### 技術スタック(確定)
- Python
- pymatgen (CIF 読み込み、構造管理)
- spglib (空間群対称操作の取得)
- 自作コード (W,t → 軸・面・中心、面の重複解消、対応管理)
- PyVista + PyVistaQt (3D 描画)
- PyQt6 または PySide6 (GUI)

旧 pygame + PyOpenGL は使わない(crystal-symmetry-puzzle v1 は独立した試作として保管)。

### 実装段階(確定)
- **段階1**: 構造ビューアー(CIF 読込、3D 表示、カメラ操作)
- **段階2**: 対称要素ビューアー(spglib 解析、軸/面/中心表示、アニメーション)
- **段階3**: パズル化(ビューアー完成後に再設計)

### 細部の判断(確定)

| 項目 | 判断 |
|---|---|
| 結合表示 | 後回し。複雑な構造を扱わない前提なので MVP に不要 |
| 鏡映面の重複解消 | 自作ロジックを実装する |
| アニメーション最適化 | 実装後に問題が出たら対処 |
| アニメーション補間 | **回転=円弧補間、鏡映/反転/並進=直線補間**(最初から) |
| パズルシステム設計 | ビューアー完成後 |
| ゲーム性の設計 | ビューアー完成後 |
| 依存ライブラリ | pymatgen + spglib で問題なし |
| 対象構造の複雑度 | 中程度まで(数百原子の構造は対象外) |

### これまでの成果物の扱い(確定)

| 旧成果物 | 新方針での扱い |
|---|---|
| SPEC v4 (旧設計書) | 段階3 パズル化時の参考資料として保管 |
| scenarios v0.1 (32点群シナリオ草案) | 同上(ただし使用機会は限定的) |
| ~/point_group/ (32点群データベース) | 段階3 で「正解判定」に使う可能性あり、保管 |
| ~/crystal-symmetry-puzzle/ v1 (pygame版) | 独立した試作として保管 |

## 3. Codex spec への補足要請(Claude が指摘した3点)

Codex spec (ChatGPT が以前作成) は概ね完成度が高いが、Ken の確定判断を受けて、以下の補足を入れた上で Codex に依頼する。

### 補足1: アニメーション補間の明示(§15.3 の修正)

Codex spec §15.3 は「最初は線形補間でよい」「将来的に改良」となっているが、Ken の確定判断により、最初から以下の通り実装する。

```
回転操作 (det(W) = +1, W ≠ I):
  軸 v, 軸上の点 p, 角度 θ を W から計算
  Rodrigues 公式で円弧補間
    pos(s) = p + R(s·θ)·(start - p)
  ここで R(α) は軸 v まわりの回転行列

らせん操作 (det(W) = +1, t に軸方向成分あり):
  回転は円弧補間 + 軸方向の並進は線形補間
  ただし簡略化のため、当面は「回転=円弧、並進=直線」を独立に合成

鏡映 (det(W) = -1, W² = I, t = 0):
  線形補間
  pos(s) = (1-s)·start + s·target

反転 (W = -I):
  線形補間(反転中心を通る)

純粋並進 (W = I, t ≠ 0):
  線形補間

映進 (det(W) = -1, t に面内成分あり):
  鏡映と並進の合成、いずれも線形補間
```

### 補足2: 鏡映面のグループ化(§9.2 の補足)

Codex spec §9.2 は鏡映面の計算式は書かれているが、**重複面の解消ロジック** が明示されていない。`search_range = 2` で探索すると同一面が複数回出るので、以下の要件を追加する。

```
鏡映面の同一性判定:
  面1, 面2 が同じ面であるとは:
    - 法線方向が平行または反平行 (|n1 · n2| > 1 - tol)
    - かつ、面1上の点が面2上にある(周期境界込みで距離が tol 以内)
  これを満たす面は1つにグループ化する。

同様に:
  - 回転軸の同一性: 方向が平行 + 軸上の点が一致(周期境界込み)
  - 反転中心の同一性: 位置が一致(周期境界込み)

グループ化後、各対称要素クラスは「複数の spglib operation_index を持つ」
データ構造になる(これは段階3 のパズル化で活用する)。
```

### 補足3: 段階1/段階2 の依頼分割

Codex spec §19 の最初の依頼リスト(10項目)は段階1 + 段階2 を全部カバーしている。
これを以下のように分割することを提案する。

```
依頼A (段階1のみ):
  1. PyVista + PyVistaQt で結晶構造ビューアーを作る
  2. pymatgen で CIF を読み込む
  3. 原子と単位胞を 3D 表示する
  4. 基本的なカメラ操作(回転、ズーム、平行移動、Reset View)
  5. 簡単な UI (Open CIF ボタン、表示 ON/OFF)

依頼B (段階2):
  6. Analyze Symmetry ボタンで spglib 解析を実行
  7. 対称操作リストを表示(分類付き: identity / rotation / mirror / etc.)
  8. 操作を選ぶと対応する軸・面・中心を 3D 表示
  9. 鏡映面・回転軸・反転中心の重複解消
  10. 操作の Play ボタンで原子をアニメーション
      - 回転は円弧補間、それ以外は線形補間
      - Selected atoms / All atoms モード切替
      - 周期境界の最近接像処理
```

分割理由:
- 段階1 が動かないと段階2 のデバッグが困難
- 段階1 だけなら数日で MVP ができる
- 段階1 で UI 感触を確認してから段階2 に進める方が安全

## 4. ChatGPT への相談事項

### 質問1: この確定方針で Codex 実装依頼に進んで問題ないか
- 方針の整合性に問題はないか
- 落とし穴になりそうな項目はないか
- 旧方針 (csp_v2) で詰めた内容のうち、新方針でも再利用すべきものがあるか

### 質問2: Claude が指摘した補足3点で十分か
- 補足1 (アニメーション補間): Rodrigues 公式での円弧補間で問題ないか
- 補足2 (鏡映面のグループ化): 同一性判定の閾値や周期境界の扱いに追加の注意点はあるか
- 補足3 (段階1/2 分割): この分割で適切か、もっと細かく分けるべきか

### 質問3: spglib 結果の分類処理について
Codex spec §8 では「W = I, t = 0 → identity」「det(W) = +1 → rotation or screw」などの分類方針が書かれているが、具体的な分類関数の実装は Codex に任せる形になっている。以下の補足が必要か:

- 回反 (S₄, S₆ など, det(W) = -1 かつ W² ≠ I) の分類条件
- 操作の Hermann-Mauguin 風表記 (4₁, m, c など) の生成
- 操作の Schoenflies 記号への対応付け

これらは段階2 でユーザーに見せる「操作リスト」のラベルに使うので、ある程度の方針は決めておきたい。

### 質問4: アニメーション時の Selected atoms モードの仕様確認
Codex spec §14, §15 では Selected atoms / All atoms モードが説明されている。
このうち Selected atoms モードで、選択された原子だけ動かす場合の挙動について確認:

- 選択原子が「対称操作で別の選択原子に移る」場合: 通常通り動かす
- 選択原子が「対称操作で非選択原子の位置に移る」場合:
  - 案A: そこに動かす(結果的に2原子が重なる)
  - 案B: アニメだけ動かして、最終位置で元に戻す
  - 案C: そもそも選択原子の集合が対称操作で閉じていない場合は警告

Claude の所感では案A が分かりやすい(対称操作の挙動を素直に見せる)が、
学習効果を考えると案B/Cもあり得る。

### 質問5: パズル化(段階3) を見据えたデータ構造の予約
ビューアー段階で考慮しておくと、パズル化が楽になる構造があるはず。
Claude の所感では:

- 各「対称要素クラス」(回転軸・鏡映面など)が、対応する operation_index のリストを持つ
- これにより、パズル化時に「同じ等価類の対称要素を1回当てればOK」「全部当てる必要あり」の切替が容易になる

これ以外に、ビューアー段階で予約すべきデータ構造はあるか?

### 質問6: pymatgen + spglib の規約整合性
pymatgen の `Structure.lattice.matrix` は各行が格子ベクトル。
spglib に渡す `cell = (lattice, positions, numbers)` の lattice も各行が格子ベクトルでよいか、
それとも転置が必要か。

これは実装時に確認すれば済む話だが、Codex に依頼する前にここの規約を spec に明記しておくと混乱を防げる。
